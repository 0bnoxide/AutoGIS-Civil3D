# New Proposal native probes: Civil 3D 2026

This is the Task 3 decision record for [issue #106](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106). It records disposable experiments in Civil 3D 2026 on 2026-09-25 and 2026-09-26. The [implementation plan](../superpowers/plans/2026-09-04-new-proposal-implementation-plan.md#task-3-prove-native-operations-before-committing-their-implementation) requires separate probes before the related production code and final qualification. The [owner handoff in #140](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/140) is the next step for company standards and templates.

The [sanitized native run evidence](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5843135341) records the pre-move hashes, relocated readback, and Sheet Set Manager check.

## Decision

**Proceed with a bounded Sheet Set implementation experiment.** In this host, in-process `AcSmComponents` COM created a DST with one sheet and one sheet-set custom property. A close and reopen returned the committed values. After the scratch folder moved, the DST resolved the moved DWG and its `Layout1`. Civil 3D's Sheet Set Manager listed the sheet and opened that layout. The DWG and DST hashes remained unchanged through the relocation checks and UI inspection. A later two-sheet synthetic run also persisted edited DST-linked fields and relative overlay Xrefs after a complete project-folder move, as detailed below.

These experiments establish feasibility for their synthetic fixtures. They do not qualify production Sheet Set integration, approved templates, company title blocks, data shortcuts, or portability across machines. The [open owner inputs](../superpowers/specs/2026-09-04-civil-production-accelerator-design.md#open-owner-inputs), including the organization's Sheet Set Manager mode and approved DWTs, still gate company-specific creation.

## Extended synthetic observations on 2026-09-26

The [A3 creation run](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5844390195) saved and independently reopened five DWGs and a two-sheet DST. Its existing-DST property edit persisted, but the title-block fields showed `####` when the DST was closed. A [read-only diagnostic](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5844519053) found that evaluating the fields while the DST remained open produced the edited property value in memory. A5 stopped on an incorrect copied-DST path assumption before mutation; its source fixtures remained unchanged. These failed attempts are retained, not counted as passes.

The independently reviewed A6 continuation passed its two native stages. It used `OpenDatabase`, `GetSheetSet`, `GetCustomPropertyBag`, `GetFileName`, and `ResolveFileName` for DST readback, and `Database.ReadDwgFile`, `EvaluateFields(FieldEvaluationContext.Demand)`, `SaveAs`, and `BlockTableRecord.GetXrefDatabase(false)` for drawing and loaded-Xref readback. It saved both synthetic title-block fields with the DST open, closed all handles, then reopened both sheets with and without the DST. Their field values and visible text were `SYNTHETIC-EDITED`, and all eight relative overlay Xrefs loaded the intended files. After the entire project folder moved, both DST sheet references resolved under the moved root, the fields still read correctly, and all eight loaded Xrefs targeted the moved DWGs. Independent hashes of five DWGs and the DST matched the reports; original fixtures and the shared host baseline were unchanged. [The sanitized evidence and report digests are on #106](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5844785178). This proves the bounded synthetic close/verify/close and relocation path, not the owner's template or Sheet Set mode.

A separate reference experiment loaded the host-installed `AcSmComponents.Interop` 25.1 assembly at runtime, without bundling Autodesk binaries, and closed/reopened one synthetic DST and sheet. [Its report is on #106](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5844519053). The running process may already have loaded that assembly, so cold first-use loading remains unproved. ADR-0008/0009 require an explicit owner decision before this becomes the production reference source.

Selected-layout DWT evidence is also synthetic. A2 and A4 each saved and independently reopened a seed DWG, DWT, and derived DWG with `SYNTH_PLAN_B` current and distinct paper-space markers in layouts A and B, but their strict host-working-database guard returned `ok:false`. Autodesk documents that managed ObjectARX wrappers can differ for one native object and that [`DisposableWrapper.Equals` compares the underlying pointer](https://help.autodesk.com/cloudhelp/2019/ENU/OARX-DevGuide-Managed/files/GUID-DB165894-208B-490E-8382-6BEF5BCA2452.htm). The corrected A5 probe passed independent cold review, then passed one Civil 3D 2026 run. Its final report SHA-256 is `E595E905A1ADDF9178543740E802FE4153D90ABA836124FAE154569F5F429778`. It saved and independently reopened all three files with the intended current layout and distinct markers; the DWT hash stayed unchanged through derivation. Every host-working-database scope matched the original native identity after disposal, and the active drawing and shared baseline stayed unchanged. Independent hashes of the three outputs matched the report. [The sanitized A5 evidence is on #106](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/106#issuecomment-5845001438). This qualifies only the selected-layout persistence path for these disposable fixtures; company DWT compatibility remains in [#140](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/140).

Data Shortcuts association remains unverified. The installed 13.8 API exposes local project-folder and drawing-association members, and a disposable probe passed source/build/reporting review, but no native command ran. Autodesk documents that project discovery uses a system-maintained [`ShortcutFolders.xml` for the Windows login](https://help.autodesk.com/cloudhelp/2026/ENU/Civil3D-UserGuide/files/GUID-0AC8F3A4-13D5-4C75-8CF0-64AD071CB2D9.htm). Neither the shared host nor a second process has qualified isolation of that state. The release must not claim automatic association. An explicit manual receipt step is proposed, pending owner disposition of the approved design's fallback condition; a future native probe needs a separately qualified login and output/profile containment.

The [receipt lifecycle and fault-injection gate](../superpowers/plans/2026-09-04-new-proposal-implementation-plan.md#task-3-prove-native-operations-before-committing-their-implementation) has [separate evidence on issue #101](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/101#issuecomment-5740833534). These probes add no receipt evidence. Complete company compatibility and final qualification require the approved manifest, DWTs, sheet conventions, and placeholder decisions in [#140](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/140).
