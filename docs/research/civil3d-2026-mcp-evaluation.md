# Civil 3D 2026 MCP evaluation

**Status:** Evaluation for owner review, 2026-09-24. Source baseline: [`3bdf45c`](https://github.com/0bnoxide/AutoGIS-Civil3D/tree/3bdf45c5d8d437f9be2a129803f9a9f34393ea43). This document authorizes no product work or installation.

## Recommendation

**Deploy none of the evaluated Civil 3D bridges now.** The shortest credible route is a small, local MCP server over this repository's existing Autodesk-free validation code. It can deliver a useful read-only package check without loading another DLL into Civil 3D. Add native inspection through the repository's one adapter only after a specific production workflow and host-version boundary have been approved and qualified. The [proposed integration plan](../plans/civil3d-2026-mcp-integration-plan.md) defines that route.

This is a source-review recommendation, not a claim that an MCP server or native bridge works. Autodesk's official preview may become a better option if Autodesk documents a supported external client connection and the target Civil 3D release. Until then, **none yet** is the operational choice.

## Scope and evidence

- Current repository tree, canonical [architecture](../architecture.md), [roadmap](../roadmap.md), source, and managed tests were checked in an isolated worktree at `3bdf45c5d8d437f9be2a129803f9a9f34393ea43`. The primary checkout and unrelated work were preserved.
- Candidate commits below are public source snapshots, inspected without copying code into this repository. A linked source line establishes what that code does; a README or release statement remains a maintainer claim. No candidate was cloned, installed, built, or run here. No candidate has been qualified in a live Civil 3D 2026 drawing by this evaluation.
- The evaluation ran on Windows with PowerShell, .NET SDK 8.0.423, Civil 3D 2026 binaries (AutoCAD 25.1 and Civil 3D 13.8), local Sonar secrets scanning, repository codebase-memory search, and public GitHub/web source access. No Civil 3D process was running, and this evaluation did not establish a licensed desktop session for a native probe. This is not a finding that the installed product lacks a license. No desktop-native request/response trace was collected. A managed compile or test pass does not establish `NETLOAD`, command, drawing, or licensed-host behavior.

## Host and protocol constraints

- [Autodesk's system requirements](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/System-requirements-for-Autodesk-Civil-3D-2026.html) distinguish 2026 through 2026.2.1 (.NET 8) from 2026.2.2 onward (.NET 10). The repository adapter is currently .NET 8; an in-process bridge must qualify the exact installed update before loading. Assembly series 25.1/13.8 alone do not resolve that update boundary. The existing [host-update issue #123](https://github.com/0bnoxide/AutoGIS-Civil3D/issues/123) owns the qualify-or-retarget decision; a .NET 8 target alone does not prove failure on the newer host.
- Autodesk's [document-lock guidance](https://help.autodesk.com/cloudhelp/2015/FRA/AutoCAD-NET/files/GUID-A2CD7540-69C5-4085-BCE8-2A8ACE16BFDD.htm) requires locks for modification from modeless or session contexts. Read-only annotations in the [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/schema#toolannotations) are hints, not enforcement. A future bridge needs native-side operation allowlists, command-context dispatch, document identity checks, bounded work, and operations that open objects only for reading. Omitting transaction commit does not prevent file, command, or other out-of-transaction side effects.
- The [official C# MCP SDK](https://github.com/modelcontextprotocol/csharp-sdk/blob/main/docs/concepts/getting-started.md/) supports local stdio servers and .NET 8; its [2.2.0 NuGet package](https://www.nuget.org/packages/ModelContextProtocol/2.2.0) is a plausible dependency for a small facade. Stdio avoids an extra network listener. A local process still has the user's file privileges, so path restrictions and result minimization remain necessary.
